# 3안 구체화 — 14일 첫 사용자 스프린트

작성일: 2026-11-19 · 대상: 비개발자 · 형태: 무료 공개 · 근거: [drafts.md](drafts.md), `research/`

이 문서의 숫자 가운데 목표치, 판정 기준, 제작 기간은 **출발점으로 잡은 초기값**이다. 리서치로 확인된 값이 아니며, 문서판 검증(9장)과 운영 기록으로 조정한다.

## 1. 무엇을 만드는가

**한 줄**: AI로 서비스를 만든 비개발자가 하루 20분씩 14일 동안 고객 대화 5건과 첫 사용자 10명에 도전하고, 끝에 계속·수정·중단을 근거를 갖고 정하게 해 주는 무료 실행 가이드.

**약속하는 것**: 14일 뒤에 "다음에 무엇을 할지"를 추측이 아니라 직접 모은 근거로 정하게 된다.

**약속하지 않는 것**: 수익, 사용자 수, 성공. 14일을 다 해도 사용자가 0명일 수 있고, 그 경우 "왜 0명인지"를 알게 되는 것이 결과다.

### 대상

| | 내용 |
|---|---|
| 누구 | 코딩을 배우지 않고 AI 도구로 웹 서비스나 앱을 만든(또는 만드는 중인) 1인 창업 초보 |
| 상황 | 만들었는데 쓰는 사람이 거의 없다. 어디에 어떻게 알릴지 모르고, 올리면 광고 취급을 받을까 봐 망설인다 |
| 가진 것 | ChatGPT·Claude 같은 AI 도구, 하루 20~40분 |
| 없는 것 | 팔로워, 광고비, 마케팅 경험, 개발 용어 지식 |
| 대상이 아닌 사람 | 이미 사용자가 수백 명 이상인 사람, 광고 집행을 배우려는 사람, 만드는 법을 배우려는 사람 |

### 들어오는 길 두 개

- **이미 만든 사람**: 14일 전체를 한다.
- **아직 만들지 않았거나 만드는 중인 사람**: 1주차(듣기)만 한다. 써 볼 링크가 없어도 할 수 있고, 만들기 전 검증이 된다.

## 2. 비개발자 대상이라서 지키는 설계 원칙

1. **한 화면에 과제 하나.** 오늘 할 일, 걸리는 시간, 끝났다는 기준만 보여 준다.
2. **용어를 쓰지 않는다.** 써야 하면 그 자리에서 풀어 쓴다. (예: "어디서 들어왔는지 표시가 붙은 링크")
3. **설치·가입이 없다.** 주소를 열면 바로 시작한다.
4. **AI에게 시킬 일은 복사해서 붙여넣는 지시문으로 준다.** 사용자가 적은 내용(고객 한 문장 등)이 지시문에 자동으로 채워진다. 사용자는 자기가 쓰던 AI에 붙여넣는다.
5. **기준선을 함께 보여 준다.** 과제마다 "보통 이 정도 반응이 나온다"를 적어, 반응이 없을 때 그것이 실패인지 보통인지 알게 한다.
6. **휴대폰에서 끝낼 수 있다.** 과제 확인과 기록 입력은 휴대폰 화면 기준으로 만든다.
7. **하루를 빼먹어도 이어진다.** 날짜가 아니라 순서로 진행한다. "14일"은 권장 속도다.

## 3. 무료 공개라서 정해지는 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 공개 범위 | 14일 과제, 양식, 채널 지도, 판정표 전부 공개. 유료 구간 없음 | 무료 특강에서 유료로 넘기는 구조는 독자가 이미 의심한다 |
| 로그인 | 없음 | 가입이 첫 번째 이탈 지점이고, 서버 비용과 개인정보 관리 부담이 생긴다 |
| 기록 저장 | 사용자의 브라우저에만 저장. 파일로 내보내기·가져오기 제공 | 서버가 필요 없다. 단, 기기를 바꾸거나 브라우저 기록을 지우면 사라지므로 화면에 분명히 알린다 |
| AI 기능 | 서버에서 AI를 돌리지 않는다. 지시문을 만들어 주고 사용자가 자기 AI에 붙여넣는다 | 무료 운영에서 사용량만큼 비용이 나가는 구조를 피한다 |
| 운영비 목표 | 도메인 비용 외 0원 | 정적 사이트와 무료 호스팅으로 가능한 범위만 만든다 |
| 수익 | 처음에는 없음 | 아래 참고 |

**수익에 대하여.** 처음 목표는 수익이 아니라 "끝까지 하는 사람이 있고, 실제로 사용자가 생기는가"의 확인이다. 그 뒤의 선택지는 광고, 가이드에서 실제로 쓰는 도구의 제휴 링크(고지 필수), 후원, 그리고 2안(코치형)을 유료로 얹는 것이다. 리서치상 광고 심사는 독자 콘텐츠가 충분한 사이트에 유리하고, 광고 수익은 트래픽 규모가 먼저이므로 지금 정하지 않는다.

## 4. 14일 과제표

각 과제는 같은 틀로 쓴다: **오늘 할 일 / 걸리는 시간 / 끝났다는 기준 / 지시문 또는 양식 / 보통 이런 반응이 나온다 / 흔한 실수**.

### 준비 (시작 전, 30~40분)

| 과제 | 끝났다는 기준 |
|---|---|
| **고객 한 문장 쓰기** — "[누구]는 [어떤 상황]에서 [어떤 문제]를 겪는다. 그래서 [무엇]을 만들었다." | 문장 속 "누구"를 듣고 실제 사람 한 명의 얼굴이 떠오른다 |
| **목표와 판정 기준 확인** — 대화 5건, 써 본 사람 10명. 14일 뒤 판정표(5장)를 미리 읽는다 | 기준을 읽고 시작 버튼을 누른다 |
| **볼 수 있게 준비** — 방문자 수와 유입 경로를 보는 무료 도구를 붙이고, 의견을 받을 창구 하나(오픈채팅방 또는 설문 양식)를 만든다. AI에게 줄 지시문 제공 | 내 서비스에 내가 들어갔을 때 방문 1건이 찍힌다 |

아직 만들지 않은 사람은 세 번째 과제를 건너뛴다.

### 1주차 — 듣기 (알리기 전에)

1주차에는 서비스 링크를 어디에도 올리지 않는다.

| 날 | 과제 | 시간 | 끝났다는 기준 |
|---|---|---|---|
| 1 | **고객이 모이는 곳 3곳 고르기.** 후보 10곳을 적고, 채널 지도(6장)를 보며 3곳으로 줄인다. 창업자·개발자가 모이는 곳이 아니라 내 고객이 질문하는 곳이어야 한다 | 20분 | 3곳의 이름과 고른 이유를 적었다 |
| 2 | **규칙 읽고 표현 모으기.** 3곳의 공지·규정을 읽고, 최근 글 20개를 훑어 사람들이 내 문제를 말할 때 쓰는 표현 5개를 그대로 옮겨 적는다 | 20분 | 표현 5개, 곳마다 "해도 되는 것·안 되는 것" 한 줄씩 |
| 3 | **질문 2개에 답하기.** 내 고객이 올린 질문에 도움이 되는 답을 단다. 링크와 서비스 이야기는 넣지 않는다 | 20분 | 답글 2개 |
| 4 | **세 사람에게 대화 요청하기.** 고객 한 문장에 맞는 아는 사람 3명에게 "15분만 이야기 들려 달라"고 연락한다. 연락 문구 제공 | 20분 | 3명에게 보냈다 |
| 5 | **대화 1~2건 하고 기록하기.** 질문지대로 묻는다. 내 서비스 설명은 맨 끝에, 상대가 물을 때만 한다 | 30~40분 | 대화 기록 1건 이상 |
| 6 | **질문 글 올리기.** 고른 곳 중 한 곳에 "이런 상황에서 다들 어떻게 하세요?"를 묻는 글을 올린다. 홍보가 아니라 질문이다 | 20분 | 글 1개, 달린 답을 기록 |
| 7 | **1주차 돌아보기.** 들은 말로 고객 한 문장과 서비스 첫 화면 문구를 고친다. 대화가 5건에 못 미치면 다음 주에 이어서 채운다 | 30분 | 고친 한 문장. 바뀐 점 한 줄 |

대화 질문지의 뼈대(전체는 양식으로 제공):

1. 최근에 이 일을 마지막으로 한 게 언제였나요? 그때 어떻게 하셨나요?
2. 그 과정에서 가장 번거로웠던 건 무엇이었나요?
3. 해결하려고 써 본 방법이나 도구가 있나요? 돈이나 시간을 들인 적이 있나요?
4. 같은 고민을 하는 사람을 한 명 소개해 주실 수 있나요?

"이런 서비스가 있으면 쓰시겠어요?"는 묻지 않는다. 대부분 예의상 "네"라고 답해서 근거가 되지 않는다.

### 2주차 — 보여 주기 (첫 사용자)

| 날 | 과제 | 시간 | 끝났다는 기준 |
|---|---|---|---|
| 8 | **첫 화면 점검.** 처음 보는 사람이 5초 안에 "누구를 위한 무엇인지" 알 수 있는지, 가입 없이 바로 써 볼 수 있는지 본다. 고칠 점은 AI에게 줄 지시문으로 바꿔 준다 | 30분 | 점검표 5문항에 답했고 1개 이상 고쳤다 |
| 9 | **문제 이야기 글 쓰기.** 서비스 자랑이 아니라 "내가 이 문제를 왜 겪었고 어떻게 풀어 봤는지"를 쓴다. 2일차에 모은 표현을 쓴다. 초안 지시문 제공 | 30분 | 글 초안 1개 |
| 10 | **첫 번째 곳에 올리기.** 그곳의 규칙에 맞는 게시판과 형식으로 올린다. 링크에는 어디서 왔는지 표시를 붙인다. 달리는 댓글에 그날 안에 답한다 | 20분 | 게시 1건. 조회·댓글·방문 수 기록 |
| 11 | **대화했던 사람에게 써 보게 하기.** 1주차에 이야기한 사람들에게 한 명씩 링크를 보낸다. 가능하면 한 명이 쓰는 모습을 옆에서(또는 화면 공유로) 본다 | 30분 | 3명에게 보냈다. 막힌 지점 1개 이상 기록 |
| 12 | **두 번째 곳에 올리거나, 낯선 5명에게 직접 연락하기.** 10일차 글을 그곳 말투에 맞게 고친다. 글을 올릴 곳이 마땅치 않으면 3일차에 답했던 사람들 같은 낯선 고객에게 개별로 연락한다 | 20분 | 게시 1건 또는 연락 5건 |
| 13 | **써 본 사람에게 세 가지 묻기.** 어디서 막혔나 / 다시 쓸 것 같나, 언제 / 이게 없어지면 아쉬울까 | 20분 | 답 3건 이상 |
| 14 | **숫자 모으고 판정하기.** 기록판의 숫자를 판정표에 넣는다 | 30분 | 계속·수정·중단 중 하나와 그 이유 한 문단 |

### 지시문 예시 (9일차)

사용자가 적은 내용이 대괄호 자리에 자동으로 들어간다.

```
아래 내용으로 커뮤니티에 올릴 글 초안을 써 줘.

- 내 고객: [고객 한 문장]
- 고객이 실제로 쓴 표현: [2일차에 모은 표현 5개]
- 대화에서 들은 이야기: [1주차 대화 기록 요약]
- 올릴 곳과 그곳의 규칙: [채널 이름, 해도 되는 것·안 되는 것]

조건:
1. 서비스 소개가 아니라 내가 이 문제를 겪고 풀어 본 과정을 쓴다.
2. 서비스 이야기는 마지막 두세 문장에만, 만든 사람이 나라는 것을 밝히며 쓴다.
3. 과장하지 않는다. 숫자는 내가 준 것만 쓴다.
4. 그곳 사람들이 쓰는 말투에 맞춘다. 광고 문구처럼 쓰지 않는다.
5. 끝에 읽는 사람에게 묻는 질문 하나를 넣는다.
```

## 5. 판정표

14일차에 세 질문에 답한다. 기준 숫자는 초기값이다.

| 질문 | 재는 것 | 통과 기준(초기값) |
|---|---|---|
| **가. 문제가 진짜인가** | 대화한 사람 중, 최근 한 달 안에 이 문제를 실제로 겪었고 스스로 해결하려 한 적이 있는 사람 | 5명 중 3명 이상 |
| **나. 닿을 수 있는가** | 지인이 아닌 사람 중 서비스를 써 본 사람 | 3명 이상 |
| **다. 다시 오는가** | 써 본 사람 중 스스로 다시 왔거나 "없어지면 아쉽다"고 답한 사람 | 2명 이상 |

| 결과 | 판정 | 다음에 할 일 |
|---|---|---|
| 가·나·다 통과 | **계속** | 반응이 나온 곳 한 곳에서 2주 더 같은 방식으로 한다. 기능 추가는 들은 요청 중 하나만 |
| 가 통과, 나 미달 | **수정 — 닿는 길** | 문제는 진짜인데 닿지 못했다. 곳을 바꾸거나 글을 고쳐 2주차를 다시 한다 |
| 가·나 통과, 다 미달 | **수정 — 서비스** | 와서 써 봤지만 남지 않았다. 13일차의 "막힌 지점"을 고치고 같은 사람들에게 다시 보여 준다 |
| 가 미달 | **수정 — 고객 또는 문제** | 고객 한 문장을 바꿔 1주차를 다시 한다. 서비스는 손대지 않는다 |
| 가 미달이 두 번 연속 | **중단을 검토** | 이 서비스를 접고, 대화에서 들은 다른 문제 가운데 하나로 1주차를 다시 시작한다 |

대화가 5건에 못 미치면 판정을 내리지 않고 "근거 부족"으로 표시한다. 대화를 채우는 것이 다음 할 일이다.

## 6. 채널 지도

곳마다 같은 항목으로 정리한다.

| 항목 | 내용 |
|---|---|
| 누가 모이나 | 어떤 사람들이 어떤 이야기를 하는 곳인가 |
| 올릴 수 있는 것 | 허용되는 글의 종류와 게시판 |
| 하면 안 되는 것 | 공지에 적힌 금지 사항 |
| 맞는 형식 | 말투, 길이, 제목 방식 |
| 보통 반응 | 직접 세어 본 값 또는 실험 기록. 표본 크기와 날짜를 함께 적는다 |
| 확인한 날과 출처 | 규정 원문 주소. 규정은 바뀌므로 "올리기 전에 공지를 다시 확인"을 항상 붙인다 |

### 첫 공개 때 넣을 곳과 현재 확인 상태

| 곳 | 현재 상태 | 비개발자 고객에게 맞는 정도 |
|---|---|---|
| 지인·직접 연락 | 방법 정리 가능(해외 경험담 다수) | 가장 먼저, 거의 모든 경우 |
| 주제별 네이버 카페 | 일반 경향 확인: 홍보 금지가 기본, 전용 홍보 게시판이나 운영진 사전 승인 사례 있음. **카페마다 공지가 우선** | 높음. 고객이 일반인일 때 주된 곳 |
| 오픈채팅·단톡방 | 사례 1건(가입은 늘었으나 사흘 뒤 남은 사람 0) | 중간 |
| 긱뉴스 Show GN | 공식 규칙 확인. 직접 집계: 하루 12~13건, 댓글 없는 글 73% | 낮음. 이용자가 기술에 익숙한 사람들이라 고객이 일반인이면 맞지 않는다 |
| 스레드 | 유입 경로로 쓰인다는 정황만 확인 | 미확인 |
| 디스콰이엇 | 등록에 검토 절차가 있다는 정황 1건. 공식 규칙 미확인 | 미확인. 만드는 사람들이 모이는 곳 |
| 당근 모임·동네 | 오프라인 모임 사례 1건 | 지역 기반 서비스일 때 |
| 오프라인 모임·현장 | 해외 경험담에서 반복 추천 | 고객이 특정 직업·취미 집단일 때 |

"미확인"인 곳은 공개 전에 규정 원문을 읽고 채운다. "보통 반응"은 첫 사례(8장)와 문서판 참가자의 기록으로 채워 나간다.

### 채널 지도가 스팸 도구가 되지 않게

- 3일차(링크 없이 답하기)와 6일차(질문 글)를 거쳐야 9일차 글쓰기 과제가 열린다.
- 같은 글을 여러 곳에 뿌리는 방법은 안내하지 않는다. 곳마다 고쳐 쓰게 한다.
- 자동 게시, 여러 계정 사용, 답변란 링크 작업은 다루지 않는다.
- 글에는 만든 사람이 본인임을 밝히게 한다. 제휴 링크가 있으면 고지 문구를 넣게 한다.

## 7. 화면 구성과 첫 공개 범위

### 화면

| 화면 | 내용 |
|---|---|
| 첫 화면 | 무엇인지, 누구를 위한 것인지, 약속하지 않는 것. 시작 버튼 하나 |
| 준비 | 고객 한 문장 작성(잘 쓴 예와 흐린 예를 나란히 보여 줌), 판정 기준 미리 보기 |
| 오늘의 과제 | 과제 하나, 시간, 끝났다는 기준, 지시문·양식, 보통 반응, 기록 입력, 완료 버튼 |
| 채널 지도 | 6장의 표. 곳별 상세 |
| 양식 모음 | 연락 문구, 대화 질문지, 대화 기록지, 글 틀, 첫 화면 점검표 |
| 기록판 | 대화 수, 써 본 사람 수, 곳별 방문·반응, 진행 일수 |
| 판정 | 기록판 숫자로 5장의 표를 자동 계산. 결과와 다음 할 일 |
| 사례 기록 | 첫 사례(8장)의 14일 기록과 숫자 |

### 첫 공개에 넣지 않는 것

로그인과 서버 저장, 서버에서 돌리는 AI, 사용자 간 커뮤니티, 결제, 자동 게시, 알림 발송, 앱. 가이드의 나머지 단계(기획, 제작, 수익화 등)는 한 화면짜리 지도로만 두고 이 스프린트로 연결한다.

### 기술

- 정적 사이트로 만든다. 과제와 양식은 글 파일로 관리해, 코드를 몰라도 내용을 고칠 수 있게 한다.
- 기록은 브라우저에 저장하고 파일로 내보내기·가져오기를 둔다.
- 호스팅은 무료 정적 호스팅을 쓴다. 저장소가 GitHub에 있으므로 GitHub Pages가 가장 단순하다.
- 방문 분석 도구를 하나 붙여 과제별 완료 수를 익명으로 센다. 사용자가 적은 내용은 수집하지 않는다.

구체적인 도구 선택은 제작을 시작할 때 정한다.

## 8. 첫 사례 — 운영 중인 할인 정보 사이트

이 스프린트를 가장 먼저 그 사이트에 적용하고 기록을 공개한다. 이 유형에서 주의할 점은 다음과 같다.

- **고객 한 문장부터 좁힌다.** "할인 정보를 찾는 사람"은 너무 넓다. 품목, 지역, 생활 상황 중 하나로 좁힌 문장을 두세 개 만들고 1주차 대화로 고른다.
- **고객이 모인 곳이 홍보를 가장 막는다.** 맘카페와 핫딜 게시판은 제휴 링크와 외부 핫딜 채널 홍보를 금지하는 경우가 많다. 2일차 규칙 읽기를 특히 꼼꼼히 하고, 금지된 곳에는 올리지 않는다. 10·12일차는 직접 연락과 문제 이야기 글 위주로 한다.
- **제휴 링크가 있으면 고지한다.** 문구와 위치는 공정거래위원회 지침과 해당 제휴 프로그램 약관 원문을 확인해 따른다.
- **"다시 오는가"가 핵심 질문이다.** 광고·트래픽 수익 모델은 재방문에 달려 있다. 13일차 질문에서 "언제 다시 올 것 같은지"를 꼭 묻는다.
- **공개 범위를 미리 정한다.** 방문자 수, 대화 내용, 실패한 시도 중 어디까지 공개할지.

## 9. 만들기 전 검증 (문서판, 약 3주)

사이트를 만들기 전에 문서로 먼저 돌려 본다.

1. **문서판 만들기(3~4일).** 14일 과제, 양식, 채널 지도 한 장, 판정표를 공유 문서로 만든다.
2. **참가자 5명 모으기.** 본인(할인 정보 사이트) 포함. 나머지는 바이브코딩 카페의 서비스 소개 게시판에 "만들었는데 사용자가 없다"고 쓴 사람들에게 개별로 제안한다. 이 과정이 곧 이 가이드의 1주차다.
3. **14일 진행.** 매일 완료 여부와 막힌 점을 메신저로 받는다.
4. **판단.**

| 볼 것 | 계속 만들 기준(초기값) |
|---|---|
| 7일차까지 간 사람 | 5명 중 3명 이상 |
| 14일차까지 간 사람 | 5명 중 2명 이상 |
| 대화 1건 이상 한 사람 | 5명 중 3명 이상 |
| 지인이 아닌 사용자가 생긴 사람 | 1명 이상 |
| 가장 많이 멈춘 과제 | 그 과제를 고치거나 쪼갠다 |

7일차 도달이 2명 이하면 사이트를 만들지 않고 과제 설계부터 다시 한다. 예상되는 가장 큰 이탈 지점은 4·5일차(대화 요청)다.

## 10. 제작 순서

기간은 추정이다.

| 단계 | 내용 | 기간 |
|---|---|---|
| 0 | 문서판 검증(9장) | 약 3주 |
| 1 | 과제 14개와 양식 글 확정(검증에서 고친 내용 반영) | 3~4일 |
| 2 | 사이트 뼈대: 첫 화면, 준비, 오늘의 과제, 브라우저 저장 | 4~5일 |
| 3 | 기록판, 판정, 내보내기·가져오기 | 3~4일 |
| 4 | 채널 지도, 양식 모음, 사례 기록 | 3~4일 |
| 5 | 비개발자 3명에게 써 보게 하고 고친 뒤 공개 | 3~4일 |

## 11. 잘되고 있는지 보는 숫자

로그인이 없으므로 익명 집계와 자발적 제출로 본다.

| 숫자 | 재는 방법 |
|---|---|
| 스프린트를 시작한 사람 | 시작 버튼 누른 수 |
| 7일차·14일차 도달 비율 | 과제 완료 버튼 누른 수 |
| 가장 많이 멈추는 과제 | 과제별 완료 수의 낙차 |
| 실제 결과(대화 수, 사용자 수, 판정) | 14일차에 "결과 공유하기"로 자발적 제출. 공개 동의를 받은 것만 사례로 싣는다 |

가장 중요한 숫자는 방문자 수가 아니라 **14일차 도달 비율**과 **지인이 아닌 사용자가 생긴 사람의 비율**이다.

## 12. 위험과 대응

| 위험 | 대응 |
|---|---|
| 읽기만 하고 실행하지 않는다 | 과제를 하루 하나로 쪼개고 끝났다는 기준을 구체적으로 적는다. 문서판 검증에서 이탈 지점을 먼저 찾는다 |
| 대화 요청(4·5일차)에서 멈춘다 | 연락 문구를 그대로 쓸 수 있게 주고, "3명 중 1명이 응하면 보통"처럼 기준선을 적는다(값은 검증으로 채움) |
| 커뮤니티 규정이 바뀐다 | 곳마다 확인한 날과 원문 주소를 적고, 올리기 전 공지 재확인을 과제에 넣는다 |
| 스팸에 쓰인다 | 6장의 규칙. 자동화·대량 게시는 다루지 않는다 |
| 브라우저 기록이 지워진다 | 저장 방식을 처음에 알리고, 7일차에 내보내기를 권한다 |
| 무료라서 유지 동기가 약해진다 | 운영비를 0원에 가깝게 둔다. 첫 사례 기록 자체가 본인 사업의 홍보 콘텐츠가 되게 한다 |
| 법·세무 내용이 틀린다 | 단정하지 않고 확인할 공식 기관을 적는다 |

## 13. 정해야 할 것

- **이름과 주소.** 강의 광고처럼 들리지 않는 이름.
- **첫 사례의 공개 범위.** 할인 정보 사이트의 방문자 수와 시행착오를 어디까지 공개할지.
- **문서판 참가자를 어디서 모을지.** 9장의 제안(바이브코딩 카페의 서비스 소개 게시판)으로 할지, 아는 사람부터 할지.
